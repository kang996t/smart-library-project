# 架构演进：副本集与分片集群（成员 B 初稿）

> 本文可合并到团队总报告的“架构演进”章节。图号应在合并时按总报告顺序统一。文中只陈述现有截图已经证明的运行结果；新增加的自动化脚本需在最终虚拟机运行后再补入最新日志数值。

## 6.1 实验环境与架构目标

成员 B 负责将单机 MongoDB 环境演进为三节点副本集，并搭建分片集群基础设施。实验环境为 CentOS Stream 10，MongoDB Server 8.3.11，mongosh 2.12.0，数据库进程统一由 `mongolab` 用户运行。副本集和分片集群使用独立端口、数据目录、日志文件及 keyfile，不与成员 A 的 27018 单机实例混用。

本实验在一台虚拟机上启动多个 MongoDB 实例，以验证复制、选举和分片路由机制。该结构适合课程实验，但所有实例仍共享同一台主机，因此不能抵御主机级故障，也不应描述为生产级高可用方案。

## 6.2 三节点副本集部署

副本集名称为 `libraryRS`。Node 1、Node 2、Node 3 分别使用 27117、27118、27119 端口；Node 1 的 priority 为 2，另外两个节点为 1。三个实例分别使用独立数据目录和日志文件，并通过同一个 `replica.key` 完成节点间内部认证。配置同时启用数据库访问控制。

初始化后，Node 1 成为 PRIMARY，Node 2 和 Node 3 成为 SECONDARY。三节点的 `health` 均为 1。实验在 PRIMARY 上写入测试图书数据并建立唯一索引，随后分别从两个 SECONDARY 读取相同集合，文档数量、主要字段和索引状态一致，证明复制链路正常。

读取偏好实验分别使用 `primary` 和 `secondaryPreferred`。`primary` 适合必须读取最新确认结果的管理操作；`secondaryPreferred` 在从节点可用时优先分担读请求，并在没有可用从节点时回退到主节点。读取偏好只能改变读路由，写入仍必须发送到 PRIMARY。

## 6.3 故障转移与业务影响

故障演练前先记录三节点角色和健康状态，再主动停止原 PRIMARY。剩余节点在选举窗口后产生新的 PRIMARY。现有过程记录包含故障发生时间、新 PRIMARY 产生时间和选举耗时分析；切换后能够重新读取原测试数据，并完成带多数写关注的测试写入。原节点重新启动后恢复为副本集成员并同步新增数据。

为了让该实验可以重复执行，仓库提供 `failover_drill.sh`。脚本会识别当前 PRIMARY、记录 UTC 时间、停止与目标配置文件精确匹配的进程、轮询新 PRIMARY、计算 `ELECTION_SECONDS`，然后执行多数写入与读取验证，最后恢复原节点。脚本要求设置 `ALLOW_FAILOVER_DRILL=YES`，避免误触发主节点停止。

仅使用 mongosh 验证切换后的读写，不足以完整说明应用程序在选举窗口内的表现。因此增加了 `replica_failover_probe.py`：探针通过 PyMongo 副本集 URI 连入三个节点，在故障演练期间持续执行主节点发现、测试 upsert 和立即读取，并把成功、失败、异常类型和延迟写成 JSONL。最终报告应根据一次真实运行结果说明：选举期间出现了多少次短暂失败、驱动是否自动发现新主节点、首次恢复成功发生在什么时间。没有真实日志时不应笼统声称“业务完全不中断”。

当前副本集成员使用 `localhost`，并只绑定 `127.0.0.1`，所以该探针应在 CentOS 虚拟机内运行。如果要让 Windows 上的成员 A 应用直接连接三个节点，则需要把 `bindIp` 和副本集成员地址改为 Windows 可达的虚拟机地址，放行相应端口，并重新验证认证和防火墙；否则驱动会收到不可达的 `localhost` 成员地址。

## 6.4 节点管理与访问控制

节点管理实验先记录三节点配置，再移除 Node 3，确认副本集以两个健康节点继续运行；随后重新启动 Node 3、将其加入配置并等待恢复为 SECONDARY，最终检查三节点数据一致性。仓库中的 `member_change_drill.sh` 固化了该过程，并拒绝在 Node 3 当前为 PRIMARY 时直接移除它。

访问控制方面，三个节点均使用 keyfile 和 `authorization: enabled`。实验创建管理账号并完成认证，使用未认证连接执行 `listDatabases` 时返回 Unauthorized，证明认证边界生效。真实密码和 keyfile 内容不进入 Git 仓库。

## 6.5 分片集群基础设施

分片实验使用一个 Config Server、两个单成员 Shard 副本集和一个 mongos：

| 组件 | 名称/角色 | 端口 |
|---|---|---:|
| Config Server | `configRS` | 27219 |
| Shard 1 | `shard1RS` | 27211 |
| Shard 2 | `shard2RS` | 27212 |
| mongos | 路由入口 | 27200 |

Config Server 使用 `clusterRole: configsvr`，两个 Shard 使用 `clusterRole: shardsvr`，mongos 通过 `configRS/localhost:27219` 获取集群元数据。四个组件均使用独立端口和日志文件，并共享 `sharding.key` 完成集群内部认证。

部署顺序为 Config Server、Shard 1、Shard 2、mongos。完成三个副本集初始化后，在 mongos 上创建并认证分片集群管理员，再使用 `sh.addShard()` 注册 `shard1RS` 和 `shard2RS`。`listShards` 和 `sh.status()` 显示两个分片均已加入，mongos 的 `hello` 结果为 `isdbgrid`。

仓库提供 `bootstrap_sharded_cluster.sh` 将初始化和注册步骤整理为幂等流程；已有副本集或已有 Shard 不会重复创建。`verify_cluster_acceptance.sh` 进一步核对四个进程的用户和配置文件、端口与 ping、认证用户、mongos 身份、Config Server 身份以及两个 Shard 的注册状态。停止与恢复实验表明，关闭进程不会删除 WiredTiger 数据目录，按正确顺序重新启动后双分片注册关系仍然存在。

成员 B 的交付边界到“可用分片集群基础设施”为止。`borrow_logs` 的分片键分析、启用 sharding、3000 条流水分布验证、定向查询与跨分片查询对比由成员 C 完成。两个 Shard 已注册并不代表业务集合已经真正分片。

## 6.6 技术问题与处理

### 6.6.1 认证初始化顺序

启用 keyfile 与访问控制后，首次初始化既需要依赖 localhost exception，又要兼容管理员已经存在的恢复场景。如果脚本始终带管理员凭据，首次部署会因为用户尚未创建而失败；如果始终不认证，恢复已有集群时又会被拒绝。解决方法是先进行无认证状态探测，再在存在凭据时尝试认证探测，只有确认尚未初始化后才使用 localhost exception 执行 `rs.initiate()`，最后创建或验证管理员。

### 6.6.2 仅检查端口可能停止错误进程

早期启停逻辑主要根据端口判断服务是否运行，但端口可能被其他进程占用。改进后的公共函数同时核对运行用户、进程名和完整配置文件路径；只有三项均匹配时才启动、停止或报告成功。未知进程占用目标端口时脚本会终止，不会直接发送信号。

### 6.6.3 故障结论缺少应用层时间线

手工截图能够证明切换前后状态，却很难连续记录驱动在选举窗口内的每次失败与恢复。为此增加 JSONL 持续探针，并把故障开始时间、新主节点产生时间和选举秒数作为机器可读输出。这样可以把“数据库发生选举”和“应用恢复成功”放在同一时间线上分析，而不是只展示最终成功画面。
